# 桃花への正式指示書｜タスク完了 → LINE自動通知システム

## 社長決定
桃花が正式タスクを完了し、GitHubの正式報告書へ完了報告を書き込んだ時点で、社長へLINEで自動的にタスク完了通知を送る仕組みを構築する。

## 1. 基本フロー
桃花がタスク実行 → タスク完了 → GitHub正式報告書へ報告 → `completed` を確認 → 自動通知起動 → LINEへ社長宛通知 → 送信receiptをGitHubへ記録。

## 2. 完了判定
- `in_progress`: 通知しない
- `completed`: タスク完了通知
- `blocked`: 問題発生通知
- `failed`: 失敗通知
- その他: 自動送信しない

報告書が更新されただけでは通知しない。正式なステータスを確認する。

## 3. LINE通知内容
実行名、Issue、ステータス、完了日時、GitHub正式報告済みであること、概要、詳細への導線を含める。実行名は前回決定した `桃花｜#Issue番号｜プロジェクト名｜作業内容` を使用する。

## 4. 二重通知防止【重要】
同じ完了報告を何度もLINE送信しない。可能な限り以下のreceiptをGitHubへ記録する。
- `task_id`
- `issue_number`
- `execution_name`
- `report_commit`
- `notification_status`
- `sent_at`
- `notification_id`

一度 `sent` になった同一完了報告は再送信しない。

## 5. 通知失敗
LINE送信失敗時は `sent` にしない。`notification_status: failed` をGitHubへ記録し、安全に再送可能にする。報告そのものを失敗扱いにはしない。

## 6. blocked / failed
`blocked` または `failed` の場合は完了通知ではなく、問題発生通知として、実行名、Issue、理由、現在の状態、社長に必要な対応を含める。

## 7. 自動化
可能な限りGitHub Actions等を利用し、GitHub報告更新 → ステータス判定 → LINE通知 → receipt記録まで自動化する。社長の手動操作を前提にしない。

## 8. セキュリティ
LINEアクセストークン等の秘密情報をソースコード、Markdown、Issue、ログへ書き込まない。GitHub Secrets等の安全な仕組みを使用する。既存のLINE連携方式がある場合は、それを優先して調査・利用すること。

## 9. テスト
最低限、以下を実施する。
1. `in_progress` → 通知されない
2. `completed` → 1回だけ通知
3. 同じ報告を再更新 → 二重通知されない
4. `blocked` → 問題通知
5. `failed` → 失敗通知
6. LINE送信失敗 → receiptがfailed
7. 再送 → 正常送信
8. GitHub上でreceipt確認

本番通知をいきなり実行せず、安全なテスト方法を採用すること。

## 10. 完成条件
桃花タスク完了 → GitHub正式報告 → `completed` 判定 → LINE自動通知 → receipt記録、が完全自動で動作し、二重通知が発生しないこと。

## 11. 完成報告
正式報告書へ、システム構成、トリガー、LINE通知方式、完了判定、二重通知防止、receipt保存場所、Secrets管理、テスト結果、実通知確認結果、残課題を記録する。

「実装した」だけでは完成扱いにしない。実際にLINEへ通知されることを確認すること。

**社長決定：この指示書を正式な桃花運用・自動通知指示として扱う。**
