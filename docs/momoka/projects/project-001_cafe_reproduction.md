## 1. プロジェクト目的

成功モデル「001」を基準音源（Master）として固定し、その音響的特徴を事実ベースで分解する。

分析 → 仮説 → 一変数検証 → 生成 → 比較 → 結果保存 → 次のPrompt設計、のループを繰り返し、001・002を再現できる生成条件を確立する。

目的は「新しい良い曲を作ること」ではなく、**001・002の再現性を高め、最終的にCafeシリーズを継続的に制作・投稿できる再現可能な制作システムを作ること**。

## 2. 基本方針

- 001を再現のMasterとして扱う。
- 002を比較・補助モデルとして扱う。
- Fact / Hypothesisを分離する。
- 1回の検証で変更する主要変数は原則1つにする。
- 「好み」ではなく、Masterとの差分を評価する。
- 推測を測定値として記録しない。
- 生成結果、分析結果、採用判断を別々に記録する。
- 成功条件はKnowledgeへ自動昇格させず、Quality Gateと人の確認を通す。

## 3. 検証ロードマップ

### Phase 1｜冒頭0〜2秒

最優先で検証する。

- Bassの存在
- Bass開始時刻
- Bassの音量立ち上がり
- Bassアタックと質感
- Piano / Drumsの侵入時刻
- クラッチ音・クリック・金属的ノイズなど不要音

### Phase 2｜Bass

- 音色
- 音域
- 発音方法
- アタック
- サステイン
- 001との一致度

### Phase 3｜Piano

- 音数
- フレーズ長
- 休符
- メロディー密度
- 動画投稿者の声を邪魔しない配置

### Phase 4｜Drums・空間・Dynamics

- ドラム特性
- リバーブ
- ステレオ幅
- 音量変化
- 全体密度

### Phase 5｜全体再現

個別検証結果を統合し、再現用Prompt・SUNO設定・Negative指定へ反映する。

## 5. A/B・実験管理

検証曲はA1、B1、C1……のようにIDを付与する。

最低限、以下を紐付ける。

`Experiment ID / 基準曲 / 派生曲 / Prompt / SUNO設定 / Negative / 変更変数 / 仮説 / 結果 / 評価 / 根拠 / 次回アクション`

A/B比較では、変更対象以外の条件を可能な限り固定する。

## 6. Fact / Hypothesisルール

例：

**Fact**：ある検証曲で0〜2秒にBassが存在しなかった。

**Hypothesis**：PromptへBass開始を明示するだけでは、SUNOの冒頭配置を保証できない。

検証によってHypothesisが `Confirmed / Rejected / Pending` のいずれかに更新される。

## 7. 現時点の重点検証

過去検証で「0:00からBass」と指定しても、実際には最初の2秒にBassが存在しなかった事例を重要なFactとして扱う。

したがって最初の重点項目は、**001の冒頭0〜2秒のBass再現**とする。

## 8. 彩花のPrompt設計ルール

Project-001で次の検証Promptを出す際は必ずセットで提示する。

1. 生成プロンプト
2. SUNO AI設定
3. ネガティブ指定

Promptは「何を再現するか」「今回何を変えるか」「それ以外は何を固定するか」が分かる形にする。

## 9. 桃花の分析・報告ルール

桃花は生成曲を分析し、Fact / Hypothesis / Evidence / Resultを整理する。

進捗・停止・未完了・ブロッカーを含む正式報告は、最新の通信規約で指定された正本へ保存する。

詳細分析ファイルを別途保存した場合は、最新報告書からリンクする。

## 10. 成功判定

単純な「良い／悪い」ではなく、以下を確認する。

- 001との差分
- 今回変更した変数の効果
- 改善 / 悪化 / 判断不能
- 再現に利用可能な条件
- 次の検証で変更すべき変数

十分な根拠がない項目は「未算出」「Pending」とする。
