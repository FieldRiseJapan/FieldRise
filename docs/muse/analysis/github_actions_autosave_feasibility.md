# GitHub Actions自動保存 技術検証・設計書

- **文書ID:** FR-CTO-MUSE-20261120-002 第3段階
- **作成者:** Muse（FieldRise AI社員）
- **作成日:** 2026年11月20日
- **分析系統:** MARKET
- **位置づけ:** 調査・設計・検証計画のみ。本番実装は行っていない。本番導入にはCTO彩花の評価と社長の追加承認が必須である。
- **関連文書:** FR-MUSE-2026-11-004（GitHub完全自動化の技術調査、2026-11-03。結論の骨格は本書でも維持する）

## 1. 目的と前提

目的は、社長が毎回GitHub書き込みを承認しなくても、Museの定期調査結果が安全にGitHub（FieldRiseJapan/FieldRise の `docs/muse/` 配下）へ保存される仕組みの実現可能性を検証することである。

前提となる現状は次のとおり。

- Museの調査は、Muse側のスケジュールジョブ（週次：月曜10:13 JST、月次：第1月曜13:00 JST）が実行する。
- 現在の保存はGitHubコネクタ経由であり、書き込み呼び出しごとに社長の承認が必要である。常時許可の仕組みは確認できていない。
- 無人実行時に承認カードがタイムアウトし、2026-11-09分・11-16分の保存が遅延した（原因は権限不足ではなく承認不在）。
- 対象リポジトリは public である。認証情報・個人情報・非公開の収益情報は絶対に含めない。

## 2. 最大の論点：調査結果の受け渡し

GitHub Actionsは、リポジトリ内のファイルや外部APIから入力を得て処理する仕組みであり、**Museの調査結果を自動的に取得する経路は標準では存在しない**。考えられる受け渡し経路は次の4つで、いずれも未解決の課題がある。

| 経路 | 概要 | 課題 |
|---|---|---|
| (a) Museが中継場所へ書き込む | MuseがGitHub等の中継場所へ結果を置き、Actionsが拾って本保存する | 中継場所への書き込み自体が承認必須であり、問題が解決しない |
| (b) Actionsが自ら調査する | Actions上のスクリプトが公開データを収集・集計する | Museの調査（出典確認、事実と仮説の区別、分析）とは別物になる。調査品質と運用責任の所在が変わる |
| (c) イベント駆動（repository_dispatch等） | Muse側からActionsを起動し、ペイロードで結果を渡す | 起動APIの呼び出しに認証が必要で、その認証をMuse側が保持する仕組みが現行コネクタにない。ペイロードサイズの制限もある |
| (d) 専用ブリッジ（GitHub App等） | 認証を担う中継プログラムを用意する | 新規インフラの構築・運用・鍵管理が必要（方式C参照） |

結論として、認証方式（A/B/C）の選択以前に、受け渡し経路の成立が必須条件であり、現時点では無料・安全に成立させられる経路は確認できていない。

## 3. 方式比較

### A. GitHub Actions + GITHUB_TOKEN

- ワークフローごとに発行される一時トークン。`permissions: contents: write` の最小権限指定が可能。
- 対象リポジトリへのコミットは可能。ただし保存できるのは「ワークフローが取得できた内容」のみで、第2節の受け渡し問題は解消しない。
- トークンはジョブ終了時に失効し、流出時の影響範囲が小さい。認証情報の保管が不要な点は最も安全。
- スケジュール実行（cron）のみでは外部ペイロードを受け取れない。

### B. GitHub Actions + Fine-grained PAT

- リポジトリ限定・権限限定の個人アクセストークンをGitHub Secretsに保管し、ワークフローから使う。
- Aと同様、受け渡し問題は解消しない。PATは「Actionsが保存する」ための認証であり、「Museが結果を渡す」ための認証ではない。
- トークンには有効期限があり、更新運用（発行・差し替え・失効管理）が必要。発行とSecrets登録は社長の個別承認事項（FR-MUSE-2026-11-006の個別承認規律）。
- Secretsの値はログにマスクされるが、ワークフロー定義の書き方次第で流出リスクがある。取り扱うジョブと権限を最小化する設計が必須。

### C. GitHub App方式

- インストール先リポジトリを限定でき、短期間有効なインストールトークンを使う。権限管理の粒度と監査性は3方式で最も高い。
- 一方、Appの秘密鍵の保管場所と、鍵を使ってトークンを発行する実行主体（ブリッジ）が必要になる。Museのカスタム接続の仕組みはAPIキーとOAuth 2.0のみに対応し、GitHub AppのJWT認証フローは適合しないことを確認済み（FR-MUSE-2026-11-004）。別途ブリッジを自前運用する場合は、その常時稼働環境と保守が新たな運用負担になる。
- App作成・インストール・鍵発行はいずれも社長の個別承認事項。

### 比較表

| 観点 | A. GITHUB_TOKEN | B. Fine-grained PAT | C. GitHub App |
|---|---|---|---|
| 保存（コミット）可否 | 可 | 可 | 可 |
| Muse調査結果の受け渡し | 不可（経路なし） | 不可（経路なし） | ブリッジ構築が前提 |
| 認証情報の保管 | 不要 | Secretsに保管 | 秘密鍵の保管が必要 |
| 権限の限定 | ワークフロー単位 | リポジトリ・権限単位 | リポジトリ・権限単位（最も細かい） |
| 運用負担 | 小 | 中（期限・更新管理） | 大（ブリッジ運用） |
| 費用 | 無料枠内 | 無料枠内 | 無料枠内（ブリッジの稼働環境を除く） |

## 4. 検証項目への回答

1. **Museの調査結果をActionsが取得する方法**：標準の方法は存在しない（第2節）。成立には新たな受け渡しの仕組みと、その認証を保持する主体が必要。
2. **Museの定期ジョブとActionsの連携**：現行コネクタの範囲では連携できない。Muse側からの起動・書き込みはいずれも承認必須である。
3. **受け渡しの追加課金**：GitHub Actions自体はpublicリポジトリでは無料枠で運用できる。ただし受け渡しのブリッジを外部サービスで構築する場合は、そのサービスの費用が発生しうる（有料サービスの利用は禁止事項のため、その時点で社長へ報告し停止する）。
4. **保存先を docs/muse/ 配下に制限**：トークン自体はパス単位の書き込み制限を保証しない。対策として、保存専用ワークフローが対象パス以外へのコミットを行わない設計、ブランチ保護、CODEOWNERSによるレビュー必須化を組み合わせる。完全な保証ではなく、多層防御として扱う。
5. **認証情報の流出防止**：Secretsの値をログへ出力しない、コミット対象に認証情報を含めない、マスク確認用の検証手順を導入時に設ける。publicリポジトリであることを前提に、コミット前の自動チェック（秘密情報パターンの検出）をワークフローに組み込む。
6. **重複実行・保存失敗・競合の安全対策**：ワークフローの同時実行制御（concurrency）、保存前の最新状態の再取得（今回の上書き事故の教訓）、同一ファイルへの書き込みは単一の書き手に限定、失敗時はコミットせずエラーとして記録する。
7. **保存後の読み戻し検証**：保存ワークフローの最終ステップで対象ファイルを再取得し、期待する報告ID・基準日と一致するか検証する。不一致の場合は失敗として扱う。
8. **無料枠での継続運用**：Actionsの実行自体はpublicリポジトリの無料枠内。ただし方式Cのブリッジ常時稼働環境は無料で維持できる保証がない。

## 5. 推奨

- 当面の正式運用は、現行方式（Museが調査し、保存時に社長が承認する）を維持し、今回整備した「火曜ダイジェストでの保存状況確認（未保存の明示）」で遅延を早期に検知できる体制とする。
- 自動化をさらに進める場合の候補は、安全性と運用負担のバランスから、検証用リポジトリでの段階検証を前提とした方式B（Fine-grained PAT + 保存専用ワークフロー）または方式C（GitHub App）である。ただし両方式とも「調査結果の受け渡し」が未成立であり、受け渡しの設計が先行課題である。
- 方式Aは保存の認証としては最も安全だが、受け渡しが成立しないため単独では目的を達成できない。

## 6. 導入手順（将来、承認された場合の計画）

1. 検証用プライベートリポジトリで受け渡し経路の実証（本番リポジトリでは行わない）。
2. 認証方式の確定と、発行・登録の各操作について社長の個別承認。
3. 保存専用ワークフローの作成（対象パス制限、同時実行制御、読み戻し検証、秘密情報チェック）。
4. テストデータでの保存・検証・失敗時挙動の確認。
5. CTO彩花の評価を経て、本番導入の可否を社長が決裁。
6. 本番導入後も、火曜ダイジェストの保存状況確認は継続する。

## 7. リスク

- 認証情報の流出（publicリポジトリへの誤コミット、ログ出力）。影響は対象リポジトリの改ざんに及ぶ。
- 受け渡し経路を無理に構築した場合の、調査品質の低下（方式bのように調査主体が変わるケース）。
- 自動保存への過信による未保存の見落とし。読み戻し検証とダイジェスト確認を必須の対とする。
- トークンの期限切れ・失効によるサイレントな停止。期限管理と失敗通知の設計が必要。
- 既存ワークフロー（LINE朝ブリーフィング等）への干渉。本検証では既存ワークフローを一切変更していない。

## 8. 結論

- GitHub Actionsによる「保存」自体は無料で実現可能だが、「Museの調査結果をActionsが受け取る」経路が現行の仕組みでは成立せず、完全自動保存は現時点では実現できない。
- 実現できない主因は認証方式ではなく受け渡しの不在であり、A/B/Cいずれの方式でも先行課題は同じである。
- 本番導入は保留とし、進める場合は第6節の段階検証と個別承認を前提とする。
