## 1. 外部HTTPSエンドポイントへのPOST送信

**実施したテスト（証拠）**
- Museの実行環境から、テスト用エンドポイント https://httpbin.org/post へダミーデータ（調査データではない検証用文字列）のJSONをPOSTし、HTTP 200で受信・返送されることを確認した（2026-11-20）。
- Museの定期ジョブは同じ実行環境で動作するため、送信機能そのものはジョブからも利用可能と判断する。

**制約**
- 送信先として使える受信エンドポイントが現時点では存在しない。受信機構の構築と、認証情報の発行は社長の事前承認が必要（本指示の実施条件）。
- 本テストの実行時にも承認カードが表示され、社長の承認を経て実行された。無人の定期実行で外部送信を伴う処理が承認カードで停止する可能性があり、「無人で確実に送信できる」ことは未確認である。

**判定：条件付きで実行可能**（送信機能は実在するが、無人運用の成立は受信先と承認の扱い次第）

## 2. repository_dispatch / workflow_dispatch の自動実行

**実施したテスト（証拠）**
- 認証なしで GitHub API の dispatch エンドポイント（POST /repos/FieldRiseJapan/FieldRise/dispatches、および actions/workflows/.../dispatches）を呼んだところ、いずれも HTTP 401「Requires authentication」が返った（2026-11-20）。当然ながら、これらの呼び出しでワークフローは起動していない。
- 現在のGitHubコネクタが提供する全46ツールを一覧で確認した。Actionsのdispatchを呼ぶツールは存在しない（ファイル読み書き、Issue、PR等のツールのみ）。書き込み系ツールはすべて呼び出しごとの承認が必須である。
- Museはコネクタの外で使えるGitHubトークンを保持していない（認証情報はプラットフォームがコネクタ経由の通信にのみ差し替える仕組みであり、Muse自身は実値を持たない）。

**判定：実行不可**（現行の手段では不可。dispatchを呼ぶにはFine-grained PATまたはGitHub App等の認証情報を新規発行し、保持主体を用意する必要があり、いずれも社長の個別承認事項）

## 3. GitHub以外の無料ストレージ経由の受け渡し

実測は行っていない（外部送信と新規認証情報の発行を伴うため、本指示の実施条件により社長承認が前提）。

- Google Drive等の接続済みストレージ：Museからの書き込みにも個別の操作が伴い、GitHub Actions側が読み取るにはGoogle側の認証情報（サービスアカウント等）の新規発行が必要になる。
- GitHub Gist：書き込みにトークンが必要であり、上記2と同じ問題がある。
- 匿名の無料ファイル共有・ペーストサービス：調査データを第三者の匿名サービスへ送ることは、情報管理と利用規約の観点で安全とはいえず、推奨しない。

**判定：未確認**（成立する経路は現時点で存在せず、いずれも新規の認証情報または承認が前提）

## 4. 現在のGitHubコネクタの承認要件を満たしたまま無人で保存する方法

- コネクタの書き込みは呼び出しごとに新規承認が必須であり、正式な事前承認・常時許可の機能は確認できていない（2026-11-03の技術調査 FR-MUSE-2026-11-004 以来、本日までの全保存で再確認）。
- 承認を迂回する方法は用いない。

**判定：実行不可**

## 5. 認証方式・費用・セキュリティ制約

- 認証方式：dispatch方式を採る場合、呼び出し側にGitHubの認証（Fine-grained PAT：対象リポジトリ限定、または GitHub App のインストールトークン）が必要。受信側ワークフローの保存には GITHUB_TOKEN（contents: write の最小権限）が使える。
- 費用：GitHub Actionsはpublicリポジトリでは無料枠で運用でき、PAT・GitHub Appの発行自体も無料である。追加課金は発生しない見込み。
- セキュリティ制約：
  - トークンはパス単位の書き込み制限を保証しない。受信側で保存先パスを検証する仕組みが必須であり、本ブランチの検証器（scripts/muse_autosave_validate.py）がその役割を担う。
  - 認証情報は公開リポジトリ・会話・通常ファイルに置かない。GitHub Secretsでの保管が前提。
  - 受け渡し契約（メタデータ、SHA-256ハッシュ、本文中のREPORT_IDと対象期間の一致、既存ファイルの無条件上書き禁止）により、誤送信・改ざん・系統混在（FIELD TESTの混入）を検出できる。

検証ブランチの検証器とテストをローカルで実行した（ネットワーク・書き込みなし）。

- 正常系（weekly）：正しいメタデータと本文で、保存先パス docs/muse/research/weekly/2026-11-16_tiktok_jazz_weekly.md が返ることを確認。
- 正常系（monthly）：保存先パス docs/muse/research/monthly/2026-11_tiktok_jazz_monthly.md が返ることを追加で確認。

- 結果：テスト4件すべて合格（unittest、2026-11-20）。

## 推奨

**推奨方式：repository_dispatch方式（受け渡し契約＋検証器つき）を本命とし、第3段階（非公開テストリポジトリでの実証）へ進むこと。**

理由：
- 受け渡し契約と検証器が既に用意されており、保存先の制限、改ざん検出、系統分離を機械的に担保できる。
- 費用は無料枠内で収まる。
- GITHUB_TOKENのみの方式（方式A）は受け渡しが成立せず、ストレージ経由は未確認事項が多い。

ただし、開始には次の社長の個別承認が必須であり、それまでは開始できない。
1. dispatch呼び出し用のFine-grained PAT（対象リポジトリ限定）の発行と、保持・呼び出し主体の確定。
2. 非公開テストリポジトリでの実証実施。

それまでの間は、現行方式（Museが調査し、保存時に社長が承認する。火曜ダイジェストで保存状況を確認する）が、無料で安全に稼働している唯一の方法として継続する。

## 実施しなかったこと

- PAT・秘密鍵等の認証情報の発行は行っていない。
- 調査データそのものの外部送信は行っていない（送信テストはダミーデータのみ）。
- 有料APIは使用していない。
