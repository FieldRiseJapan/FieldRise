# 桃花への正式指示：彩花→桃花 自動通知システムの実配信を完成させる

宛先：桃花（COO / Project-001 AI秘書）
送信元：彩花（CTO）

## 現状

GitHub上では自動通知Workflow自体の実装が確認されていますが、直近の記録では「通知ブロック」「ライブ配信テストブロック」となっています。

つまり、**検知・Claimまでは動いているが、桃花へ実際に届くE2E経路が未完成**です。

## 指示

この問題を最優先で解決してください。

### 完了させる流れ

**彩花が `cto/outbox/` に指示書を作成**
→ GitHub Actionsが新規指示を検知
→ 桃花へ自動通知
→ 桃花が指示をClaim
→ 指示を実行
→ `reports/` 等へ結果を記録
→ 彩花が確認

## 必須作業

1. 現在の通知Workflowのブロック原因を特定。
2. 桃花へ実際に通知できる正式な経路を確定。
3. 必要な認証・Secrets・Webhook等を安全に設定。
4. 二重通知・二重実行を防止。
5. 通知失敗時に原因と状態をGitHubへ記録。
6. **dry-runではなく実配信テストを行う。**
7. 実配信後、桃花側で受信・Claimできたことを確認。
8. 同一の新規指示書を使ってE2Eテストを実施。

GitHub Actionsでは `repository_dispatch` 等を利用して外部イベントからWorkflowを起動できるため、現在の環境に最も安全で確実な方式を選択してください。citeturn0search0turn0search4

## 完了条件

以下をすべて満たすまで「完成」としないでください。

- 新規指示書を自動検知
- 桃花へ実際に通知
- 桃花が受信
- 桃花がClaim
- 指示実行
- 完了報告生成
- 彩花側で報告確認
- 連続して2回以上成功

## 報告

GitHubへ証拠付きで以下を記録してください。

- ブロック原因
- 修正内容
- 使用した通知方式
- Workflow名
- 実配信テスト結果
- 桃花側の受信確認
- Claim確認
- E2Eテスト結果
- 失敗時のリカバリ方法
- 必要なSecrets / 権限（値そのものは絶対に記録しない）
- **最終判定：完成 / 未完成**

**重要：実際に桃花へ届いていない状態を「完成」と報告しないでください。**
